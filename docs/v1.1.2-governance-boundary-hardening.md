# Planscope Governance Boundary Hardening Guide

> Status: Proposed reusable design update  
> Scope: Planscope itself, independent of any consuming repository  
> Goal: Preserve Planscope's small-context planning model while making the boundary between planning state and authoritative project knowledge explicit and enforceable.

## 1. Why this change is needed

Planscope already has a clear strength: it governs `.planning/` as a bounded, lifecycle-aware execution context.

Its current model is strong at:

- routing through `INDEX.md`;
- maintaining exactly zero or one active release;
- making `PLAN.md` authoritative for current phase/task/blockers/next action;
- keeping `KNOWLEDGE.md` selective;
- rotating `LOG.md`;
- archiving completed releases;
- checking structural invariants through `plan doctor`;
- limiting planning-file growth through budgets and compaction.

The remaining design gap is at the boundary between **planning memory** and **authoritative repository knowledge**.

Today, a consuming project may have durable truth in:

- product specifications;
- architecture documents;
- contracts and schemas;
- release policies;
- runbooks;
- test instructions;
- version history;
- source code and machine-readable configuration.

Planscope currently tells agents how to manage planning files, but it does not state strongly enough that `.planning/` must not become a competing source of truth for those project artifacts.

This can cause a long-running project to develop two parallel knowledge systems:

```text
Tracked repository authority
├─ docs/
├─ README.md
├─ AGENTS.md
├─ schemas / contracts
└─ source configuration

Planning authority
├─ PROJECT.md
├─ PLAN.md
└─ KNOWLEDGE.md
```

The intended model should instead be:

```text
Tracked repository authority
        ↑
semantic promotion
        ↑
.planning/
(execution context + temporary durable memory)
```

Planscope should route and preserve context, not silently replace project documentation governance.

---

## 2. Design objective

The reusable rule for every Planscope project should be:

> `.planning/` owns execution context and non-recoverable working knowledge.  
> Durable project truth belongs in the repository's authoritative source when such a source exists.

This preserves Planscope's original purpose:

> Persistent memory. Small working context.

The change must **not** turn Planscope into a documentation framework, static-site generator, policy engine, architecture linter, or repository-specific compliance system.

---

## 3. New core invariant

Add the following invariant to `SKILL.md` near the primary planning rules.

```md
## Project Authority Boundary

Planscope is not the authoritative project documentation system.

`.planning/` owns:

- active release execution state;
- current task/phase/blocker/next-action state;
- temporary recovery context;
- release-scoped findings that cannot yet be promoted;
- compact cross-release context that has no better authoritative home.

Tracked repository artifacts should own durable project truth when available,
including product requirements, architecture contracts, public procedures,
schemas, compatibility policy, release evidence, and source-controlled facts.

Do not duplicate an authoritative project rule into `.planning/` merely for
convenience. Route to the authoritative source instead.

When a planning finding becomes durable, promote it to the best authoritative
project destination. Use `PROJECT.md` only when no better recoverable source exists.
```

This must be a **core rule**, not optional guidance buried in design documentation.

---

## 4. Redefine `PROJECT.md`

### Current risk

A broad definition such as:

```text
Architecture
Core Constraints
Stable Domain Knowledge
Long-Term Decisions
```

can encourage `PROJECT.md` to become a second product specification.

### New responsibility

`PROJECT.md` should be defined as:

> A compact cross-release routing and residual-context document, not the default destination for all durable knowledge.

Recommended responsibility:

```md
### PROJECT.md

Use for:

- project authority routing;
- compact cross-release constraints that are not reliably encoded elsewhere;
- durable decisions whose authoritative project destination does not yet exist;
- short context needed to interpret multiple releases.

Prefer links or repository-relative paths to authoritative tracked artifacts.

Do not duplicate:

- product specifications;
- architecture documents;
- public runbooks;
- schemas/contracts;
- release evidence;
- test manuals;
- facts already directly recoverable from source/configuration.
```

---

## 5. Update the `PROJECT.md` template

Replace the current broad template with a routing-first template.

Recommended template:

```md
# Project Context

## Authority Map

- Product requirements: [path or "not defined"]
- Architecture: [path or "not defined"]
- Release / compatibility policy: [path or "not defined"]
- Test instructions: [path or "not defined"]
- Operational runbooks: [path or "not defined"]
- Version / release evidence: [path or "not defined"]

## Cross-Release Constraints

- [constraint not reliably recoverable elsewhere]

## Stable Context

[Only context that future work needs and that does not have a better
authoritative repository home.]

## Long-Term Decisions

### D-001

Decision:

[...]

Authoritative destination:

[path, or "PROJECT.md — no better source"]

Reason:

[...]
```

The authority map is intentionally generic. Planscope does not prescribe which files a project must use.

## 6. Generalize the existing recoverability principle

Planscope already applies a strong rule to `KNOWLEDGE.md`:

> Store information only when future work may need it and it cannot be reliably recovered from ordinary source files.

Promote that concept to the whole planning system.

New general rule:

```md
## Recoverability Rule

Before writing durable information into `.planning/`, ask:

1. Is this information already recoverable from source, tests, configuration,
   tracked documentation, Git history, or another authoritative artifact?
2. If yes, store only a route/reference when planning context needs it.
3. If no, keep it in the narrowest planning scope that can preserve it.
4. When an authoritative destination later exists, promote it there and remove
   the duplicate planning copy.
```

This should apply to `PROJECT.md`, `PLAN.md`, and `KNOWLEDGE.md`, not only knowledge findings.

## 7. Change semantic release closing

### Current conceptual flow

The existing release-close guidance effectively favors:

```text
release KNOWLEDGE
      ↓
PROJECT.md
```

That is too narrow for real repositories.

### New flow

Semantic closing should classify durable findings by destination:

```text
release finding
      ↓
classify
      ├─ product requirement → project product/spec authority
      ├─ architecture rule   → architecture authority
      ├─ procedure           → runbook/workflow authority
      ├─ contract/schema     → machine-readable contract/spec
      ├─ release evidence    → version/release evidence location
      ├─ source fact         → source/configuration itself
      └─ no better home      → PROJECT.md
```

Recommended replacement for the semantic-close section:

```md
Semantic close (your job), in order:

1. verify release acceptance criteria;
2. create `SUMMARY.md`;
3. review release findings and decisions;
4. promote each durable item to its best authoritative project destination;
5. use `PROJECT.md` only for cross-release context with no better recoverable home;
6. remove or compress planning copies that would compete with the promoted authority;
7. update `ROADMAP.md`;
8. set PLAN `## Status` to `complete`;
9. complete the PLAN closeout checklist;
10. run `plan.py close <version>`.
```

## 8. Add an explicit closeout checklist to `PLAN.md`

Planscope cannot semantically understand every consuming repository, but it can require the agent to perform an explicit reconciliation step.

Recommended `PLAN.md` template addition:

```md
## Closeout

- [ ] Acceptance criteria verified
- [ ] Durable findings classified
- [ ] Durable project rules promoted to authoritative repository sources where applicable
- [ ] Release evidence written to its durable destination where applicable
- [ ] Superseded planning copies removed or compressed
- [ ] PROJECT.md contains no avoidable duplicate of an authoritative project rule
- [ ] ROADMAP.md updated
- [ ] SUMMARY.md created
```

This checklist should be reusable across projects because it does not assume a `docs/` layout.

---

## 9. Make `plan close` validate closeout mechanically

`plan close` should not attempt semantic repository analysis.

It should only verify that the required closeout checklist exists and all required items are checked.

Suggested behavior:

```text
error: PLAN closeout is incomplete:
- Durable project rules promoted to authoritative repository sources where applicable
- PROJECT.md contains no avoidable duplicate of an authoritative project rule
```

A force option may remain available if Planscope already supports forced close semantics, but normal close should require the checklist.

This creates useful pressure without pretending the CLI can judge project meaning.

---

## 10. Extend `plan doctor` only inside Planscope's boundary

Do **not** make `doctor` crawl the entire repository looking for contradictory Markdown.

That would turn Planscope into a repository governance engine.

Reasonable additions:

### Validate PROJECT routing shape

If the new template is adopted, `doctor` may check that:

- `## Authority Map` exists;
- no duplicate authority keys exist;
- paths, when explicitly provided and repository-relative, can optionally be checked for existence.

The last check should be conservative and optional because projects may use URLs, generated artifacts, or non-file authorities.

### Validate PLAN closeout schema

`doctor` may check:

- `## Closeout` exists for active releases created under the new format;
- recognized closeout items are parseable;
- a release marked `complete` cannot have unchecked required closeout items.

This remains structural, not semantic.

---

## 11. Clarify `INDEX.md` responsibility

`INDEX.md` should route not only within `.planning/`, but may also expose a very small set of project authority pointers when they are directly relevant to the active work.

Do not turn INDEX into a documentation table of contents.

Recommended rule:

```md
INDEX may contain a compact Project Authority pointer or two when the active
release depends on them. The full authority map belongs in PROJECT.md or the
project's own tracked documentation.
```

Example:

```md
## Context Map

Active plan:
`releases/v1.2/PLAN.md`

Relevant project authority:
`docs/release-policy.md`
```

---

## 12. Clarify what belongs in PLAN

Add:

```md
PLAN should describe intended release work and acceptance criteria.

When a task changes a durable project rule, PLAN should name the authoritative
artifact that must be updated. PLAN must not become the final specification for
that rule unless the consuming project explicitly defines it as such.
```

Example:

```md
### T-014 Change compatibility policy

Deliverables:

- update implementation;
- update authoritative compatibility specification at `docs/...`;
- update tests;
- record release-specific evidence.
```

This is a portable pattern across repositories.

---

## 13. Clarify what belongs in KNOWLEDGE

Keep the existing recoverability gate and add promotion state.

Recommended finding structure:

```md
### F-014

Scope: release

Finding:
[...]

Recoverable from ordinary project sources:
no

Promotion target:
`docs/architecture.md` / `PROJECT.md` / pending

Status:
temporary / promoted
```

Do not require every finding to use every field if that would make the skill heavy; the important addition is the concept of an explicit promotion target.

---

## 14. Preserve Planscope's non-goals

The following must remain out of scope:

- deciding what a project's product documentation hierarchy must be;
- enforcing a specific `docs/` directory;
- parsing arbitrary domain specifications;
- detecting semantic contradiction across all Markdown;
- replacing Git history;
- replacing issue trackers;
- automatically rewriting tracked specifications;
- automatically promoting knowledge through LLM-generated edits;
- repository-wide architecture enforcement;
- source-code/static-analysis policy enforcement.

Planscope should create the lifecycle checkpoint; the consuming repository decides how its authority is structured.

---

## 15. Versioning and backward compatibility

This is a behavior-level skill update because it changes:

- `PROJECT.md` responsibility;
- release-close semantics;
- `PLAN.md` template requirements;
- possibly `plan close` and `plan doctor`.

Recommended migration behavior:

### Existing projects

Do not require immediate rewriting of historical archived releases.

For the active release:

1. add `## Closeout` if missing;
2. add or migrate `PROJECT.md` toward `## Authority Map`;
3. classify existing PROJECT content:
   - keep residual cross-release context;
   - replace duplicated project rules with links where practical;
4. continue normally.

### Archived releases

Treat as historical. Do not rewrite solely to satisfy the new template.

### Empty/no-active-release projects

Apply the new templates at next `open`.

## 16. Suggested implementation workstreams

### P1 — Skill semantics

Update:

- `SKILL.md`;
- `PROJECT.md` template;
- `PLAN.md` template;
- `SUMMARY.md` guidance if it currently implies PROJECT is the only promotion target.

### P2 — CLI structural enforcement

Update:

- PLAN parsing for Closeout;
- `plan close`;
- `plan doctor`;
- tests for incomplete closeout;
- tests for complete closeout;
- migration-safe behavior for older active plans if required.

### P3 — Documentation

Update:

- README overview;
- design rationale;
- compatibility notes only if tool behavior changes;
- examples demonstrating authority routing.

### P4 — Dogfood verification

Use Planscope's own repository to verify:

- product docs remain under `docs/`;
- `.planning/PROJECT.md` routes to them instead of duplicating them;
- release findings promote to the right destination;
- close cannot succeed before authority reconciliation is acknowledged.

## 17. Acceptance criteria

The design update is complete when all of the following are true:

- `SKILL.md` explicitly states that Planscope is not the authoritative project documentation system.
- `.planning/` is defined as execution context plus non-recoverable working knowledge.
- `PROJECT.md` is routing-first and no longer the default sink for all durable knowledge.
- the recoverability rule applies across planning files.
- semantic close promotes durable information to the best project authority, not automatically to PROJECT.
- `PLAN.md` includes an authority-reconciliation closeout checklist.
- normal `plan close` refuses an incomplete required closeout.
- `plan doctor` can detect structurally incomplete closeout state.
- archived releases do not need retroactive migration.
- no repository-specific documentation layout is hard-coded.
- Planscope still does not attempt repository-wide semantic documentation analysis.

---

## 18. Resulting reusable model

After the change, Planscope's model becomes:

```text
Authoritative project artifacts
        ↑
        │ semantic promotion
        │
PROJECT ├── residual cross-release context + routing
        │
PLAN / KNOWLEDGE / LOG
        │
        ↓
active execution context
```

The key distinction is:

> Planscope remembers enough to continue work safely.  
> The repository remains responsible for what the project officially means.

That boundary keeps Planscope small, portable, and reusable while closing the most important lifecycle gap exposed by long-running real-world use.

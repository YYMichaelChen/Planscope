# Planscope v1.1.0 Development Update

**Version:** v1.1.0
**Codename:** Hardening
**Status:** Development Specification
**Target:** First stable public iteration after v1.0
**Project:** Planscope
**Repository:** `YYMichaelChen/Planscope`

> Persistent memory. Small working context.

# 1. Overview

Planscope v1.1.0 is a **correctness, lifecycle, context-efficiency, and distribution hardening release**.

v1.0 established the core model:

```
Persistent Knowledge
        ↓
Scoped Storage
        ↓
Context Routing
        ↓
Small Working Set
        ↓
Agent
```

The first version successfully introduced:

- `.planning/` as the canonical planning namespace;
- project / roadmap / release / working-context separation;
- `INDEX.md` as the context router;
- release-scoped `PLAN.md`, `KNOWLEDGE.md`, and `LOG.md`;
- archival release lifecycle;
- bounded document budgets;
- lightweight helper CLI;
- one canonical Skill source;
- multi-tool portability.

v1.1.0 does **not** introduce a new architecture.

Its purpose is to make the existing architecture reliable enough for sustained real-world usage.

The primary objective is:

> **Make active planning context deterministic, internally consistent, and cheap to recover across long-running development.**

# 2. Why v1.1.0 Exists

Dogfooding v1.0 exposed several lifecycle and consistency issues.

The conceptual architecture is sound, but the first implementation still allows active planning state to drift.

The main problems are:

1. Opening or closing a release does not atomically update the complete active working set.
2. Multiple release directories may coexist even though Planscope assumes one active release.
3. Release completion validation can accept malformed or unknown phase states.
4. Release closing currently mixes semantic work with post-archive cleanup.
5. `INDEX.md`, `PLAN.md`, and `LOG.md` duplicate active-state fields and may drift.
6. Context routing can be made more selective by reading sections instead of whole planning files.
7. LOG rotation can overwrite previous archives created on the same day.
8. The doctor command does not yet validate all important planning invariants.
9. Project-level installation does not yet provide a single-command installation path for every supported agent.
10. Legacy development documentation can be confused with active planning state.

v1.1.0 addresses these issues without turning Planscope into an agent runtime.

# 3. Release Philosophy

v1.1.0 follows three rules.

## 3.1 Correctness before features

No new major planning concepts are introduced until lifecycle behavior is deterministic.

## 3.2 Mechanical consistency belongs to tools

Agents remain responsible for semantic decisions.

Scripts should handle:

```
state synchronization
path validation
naming validation
budget validation
release transitions
mechanical consistency
```

Agents should handle:

```
planning
summarization
knowledge selection
decision making
knowledge promotion
```

## 3.3 Active context must stay bounded

The success of Planscope is not measured by how much information it stores.

It is measured by how little information the agent must load to safely continue working.

# 4. Scope

v1.1.0 contains four workstreams:

```
P1 — Core Lifecycle Hardening
P2 — Context Efficiency
P3 — Distribution
P4 — Verification
```

# 5. Non-Goals

The following are explicitly excluded from v1.1.0:

- `state.json`
- database-backed state
- event sourcing
- semantic vector search
- lifecycle hooks
- autonomous task loops
- multi-agent coordination
- task DAGs
- agent leases
- automatic LLM summarization
- transcript recovery
- automatic project knowledge promotion
- automatic architecture inference
- remote services
- telemetry
- background daemons

If a proposed change requires any of these, defer it until after real-world v1.x usage.

# 6. P1 — Core Lifecycle Hardening

## T-101 — Atomic Active Release Activation

### Problem

`plan open <version>` currently updates the Active Release pointer but does not reset or synchronize the entire active working set.

This can leave stale values in:

```
Current Focus
Current Phase
Next Action
Current Blockers
Context Map
```

Example invalid state:

```
Active Release:
v1.2

Current Focus:
T-014 from v1.1

Active Plan:
releases/v1.1/PLAN.md
```

This violates the core Planscope guarantee that `INDEX.md` accurately represents the active working set.

### Required change

Replace narrow active-release editing logic with a dedicated release activation operation.

Recommended internal API:

```
activate_release(planning_root, version)
```

The operation must update all release-dependent INDEX fields.

After:

```
plan open v1.2
```

INDEX must contain:

```
## Active Release

v1.2

Path:
releases/v1.2

## Current Focus

Not selected.

## Current Phase

Not started.

## Next Action

Define the release objective and first phase.

## Current Blockers

None.
```

Context Map must point to:

```
releases/v1.2/PLAN.md
releases/v1.2/KNOWLEDGE.md
releases/v1.2/LOG.md
```

### Acceptance criteria

- Opening a release removes references to the previous release.
- INDEX contains no stale Task ID.
- INDEX contains no stale Phase.
- INDEX contains no stale release path.
- `plan doctor` passes immediately after `plan open`.
- Repeated parsing of INDEX resolves only the newly opened release.

# 7. T-102 — Atomic Active Release Clearing

### Problem

Closing a release currently clears only part of the active-release state.

A closed release must disappear completely from the active working context.

### Required change

Introduce:

```
clear_active_release(planning_root)
```

After closing the active release, INDEX should become equivalent to:

```
## Active Release

none

Path:

## Current Focus

None.

## Current Phase

None.

## Next Action

Open the next release or select new work.

## Current Blockers

None.
```

Release-dependent Context Map fields must either be empty or explicitly state that no active release exists.

They must never reference archived content.

### Acceptance criteria

After:

```
plan close v1.1
```

all of the following must be absent from active INDEX:

```
releases/v1.1
T-* belonging to v1.1
P* belonging to v1.1
old Next Action
old blocker
```

# 8. T-103 — Single Active Release Invariant

### Principle

Planscope v1.x supports:

```
exactly zero or one active release
```

It does not support multiple concurrent active releases.

### Required behavior

If:

```
.planning/releases/v1.1/
```

already exists, then:

```
plan open v1.2
```

must fail.

Suggested error:

```
error: Active release v1.1 already exists.
Close it before opening v1.2.
```

`plan doctor` must treat multiple active release directories as a failure.

Current behavior:

```
WARN
```

New behavior:

```
FAIL
```

### Acceptance criteria

These states are valid:

```
releases/
(empty)
```

or:

```
releases/
└── v1.1/
```

This state is invalid:

```
releases/
├── v1.1/
└── v1.2/
```

# 9. T-104 — Strict Phase Status Validation

### Problem

Completion currently relies on recognizing unfinished states.

This creates a false-completion risk.

For example:

```
Status:
blocked
```

may not be considered unfinished and may therefore escape the close gate.

### Canonical Phase states

v1.1.0 must define only:

```
pending
in_progress
complete
```

No other value is valid.

### Required validation

For every Phase:

```
phase.status in {
    "pending",
    "in_progress",
    "complete",
}
```

Anything else is invalid.

Examples of invalid values:

```
blocked
done
finished
in-progress
started
Complete
```

### Completion rule

A release is mechanically closeable only when:

```
all(phase.status == "complete" for phase in phases)
```

Do not implement completion as:

```
not any(status in ("pending", "in_progress"))
```

### Release-level status

PLAN must also contain:

```
## Status

complete
```

before normal close is allowed.

### Acceptance criteria

Close must fail if:

- any Phase is `pending`;
- any Phase is `in_progress`;
- any Phase has an unknown status;
- any Phase has no status;
- PLAN release-level Status is not `complete`.

# 10. T-105 — Release Close Lifecycle Correction

### Existing ambiguity

The intended lifecycle is:

```
Verify
↓
Generate SUMMARY
↓
Review KNOWLEDGE
↓
Promote durable knowledge
↓
Update roadmap
↓
Archive
```

The mechanical `close` command currently archives before all semantic work is necessarily complete.

This creates a contradiction with another Planscope rule:

> Archive should not be part of default context.

### New rule

`plan close` becomes the **final mechanical commit of a release**.

Semantic close must happen first.

The full lifecycle becomes:

```
Agent Semantic Close
        ↓
Verification
        ↓
SUMMARY creation
        ↓
Project knowledge promotion
        ↓
ROADMAP update
        ↓
PLAN status = complete
        ↓
Mechanical Close
        ↓
Archive
```

### CLI behavior

After successful close, do not tell the Agent to reopen archive to perform normal promotion work.

Instead output something equivalent to:

```
Closed v1.1.
Release moved to archive.
Active release cleared.
```

### Acceptance criteria

Normal close requires:

- all phases complete;
- PLAN Status complete;
- SUMMARY exists.

Semantic promotion is documented as a prerequisite, not post-close work.

# 11. T-106 — Safe LOG Rotation

### Problem

Current archive naming can collide when multiple LOG rotations happen on the same date.

Example:

```
v1.1-LOG-2026-09-26.md
```

A second rotation can overwrite the first.

### Required change

Use collision-safe archive names.

Recommended:

```
v1.1-LOG-2026-09-26-001.md
v1.1-LOG-2026-09-26-002.md
v1.1-LOG-2026-09-26-003.md
```

or timestamp-based:

```
v1.1-LOG-20260926T173501.md
```

No existing archive may ever be silently overwritten.

### Recommended secondary improvement

Prefer rotating activity at entry boundaries such as:

```
### 2026-09-26
```

instead of splitting purely by line count.

This is recommended but not required if it significantly increases implementation complexity.

### Acceptance criteria

Running compact multiple times in one day creates distinct archives.

# 12. T-107 — Expand Doctor Invariants

`plan doctor` becomes the authoritative mechanical health check.

It should validate the following.

## Root structure

Required:

```
.planning/
├── INDEX.md
├── PROJECT.md
├── ROADMAP.md
├── releases/
└── archive/
```

Missing required root components must fail.

## Active release count

Allowed:

```
0 or 1
```

More than one:

```
FAIL
```

## Active release contents

If active:

```
PLAN.md
KNOWLEDGE.md
LOG.md
```

must exist.

## Illegal files

Existing filename validation remains.

Additionally reject unknown active planning directories.

For example:

```
.planning/temp/
.planning/drafts/
.planning/releases/v1.1/notes/
```

must fail unless explicitly permitted by the specification.

Archive remains exempt from active-structure rules.

## PLAN schema

Required sections:

```
Objective
Acceptance Criteria
Status
Current
Phases
Blockers
Next Action
```

## Status validation

Validate canonical status values.

## INDEX consistency

Check:

```
INDEX Active Release
==
actual release directory
```

and where values exist:

```
INDEX Current Phase
==
PLAN Current Phase
INDEX Next Action
==
PLAN Next Action
```

Drift should be reported.

### Failure policy

Structural invalidity:

```
FAIL
```

Recoverable active-state drift:

```
WARN
```

until `plan sync` is implemented.

# 13. P2 — Context Efficiency

## T-201 — Add `plan sync`

### Purpose

Remove unnecessary manual synchronization between:

```
PLAN
INDEX
LOG
```

The canonical active task state should primarily live in PLAN.

INDEX should behave as a lightweight routing projection.

### Command

```
plan sync
```

### Source fields

Read from active PLAN:

```
Current Phase
Current Task
Next Action
Blockers
```

### Target

Synchronize corresponding active routing fields in:

```
INDEX.md
```

LOG must not be rewritten simply to mirror state.

LOG remains a historical/recovery document.

### Principle

```
PLAN = active release work source
INDEX = context routing projection
LOG = rolling execution history
```

### `status`

`plan status` should prefer PLAN values when an active PLAN exists.

### `doctor`

If INDEX and PLAN drift:

```
WARN INDEX current state is stale.
Run: plan sync
```

### Acceptance criteria

After changing PLAN manually:

```
plan sync
```

must restore INDEX consistency without semantic inference.

# 14. T-202 — Search Before Full Read

### Current improvement opportunity

Planscope already avoids loading all planning files.

v1.1.0 should go one step further:

> A planning file is a retrieval source, not necessarily an atomic context unit.

### Add to SKILL.md

Recommended rule:

```
Prefer search + bounded reads over full-file reads.
```

### PLAN retrieval

For normal Feature work:

prioritize:

```
Current
active Phase
Blockers
Next Action
```

Do not automatically read every completed phase.

Full PLAN reads are mainly for:

```
planning
replanning
release review
recovery
```

### KNOWLEDGE retrieval

Search first using:

```
Task ID
Phase ID
Finding ID
Decision ID
keywords
```

Then read relevant sections.

Do not read the entire KNOWLEDGE file by default.

### PROJECT retrieval

Read only for:

```
architecture
stable constraints
cross-release decisions
project conventions
```

### Archive

No change:

```
never automatically load archive
```

# 30. Success Metrics

The release should be judged against these qualitative metrics.

## Context stability

As repository history grows, routine active-context size should remain roughly constant.

## Recovery efficiency

A new Agent session should usually recover from:

```
INDEX
+ active PLAN context
+ relevant knowledge
```

without reading historical releases.

## Maintenance efficiency

A normal Task completion should require only a small bounded number of Planning edits.

## Lifecycle correctness

No archived release may remain accidentally referenced as active context.

## Format stability

Different Agents and sessions should continue producing the same planning structure.

# 31. Regression Principles

Any future change should be rejected if it causes one of the following:

```
more files must always be read
more files must always be updated
history automatically enters active context
the Agent has to maintain duplicated state manually
new planning filename types appear without strong justification
mechanical state transitions depend on model judgment
```

# 32. Migration

v1.0 projects should require no manual migration.

On existing `.planning/` directories:

```
plan doctor
```

should identify inconsistencies.

Recommended upgrade procedure:

```
git pull
python install.py --project .
python .agents/skills/planscope/scripts/plan.py doctor

```

If multiple active releases exist, users must explicitly choose one before normal operation resumes.

Do not silently archive or delete ambiguous release state.

# 34. Release Notes Draft

## Planscope v1.1.0

Planscope v1.1.0 hardens the scoped-planning model introduced in v1.0.

This release focuses on keeping active context correct and small during long-running development.

### Highlights

- Atomic active-release switching
- Strict single-active-release enforcement
- Safer release completion validation
- Corrected release-close lifecycle
- New `plan sync` command
- Stronger `plan doctor` invariants
- Collision-safe rolling LOG archives
- More selective section-level context retrieval
- Unified project installation across supported agents
- Patch-version support

The core philosophy remains unchanged:

> **Persistent memory. Small working context.**

v1.1.0 deliberately does not add databases, agent runtimes, hooks, semantic search, or multi-agent scheduling.

Planscope remains Markdown-first, portable, and intentionally small.

# 35. Definition of Done

Planscope v1.1.0 is complete when the following statement is true:

> A developer can install Planscope into a fresh project, open one release, work across multiple sessions, recover with bounded context, synchronize active planning state mechanically, compact working documents, safely close the release, archive its history, and start the next release without stale context leaking forward.

If this workflow works consistently across the supported agents, v1.1.0 is ready.

```
How often does INDEX drift?

How often is archived information reopened?

Which documents still grow too quickly?

Which CLI operations actually save Agent work?
```

Only features justified by actual recurring usage problems should enter the next release.

The threshold for new architecture should remain high.

# Final Principle

Planscope should become better by requiring the Agent to manage **less**, not more.

The long-term invariant is:

```
Project history grows.

Persistent storage grows.

Active working context does not.
```

That is the design target for v1.1.0.
